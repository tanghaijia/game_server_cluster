# 调度器调度需求分析（Scheduler Requirements）

- 状态：草稿 v1
- 范围：controller-go 调度器（`internal/biz` Scheduler）及周边数据模型
- 输入：产品需求清单（R1-R9）+ 需求确认决策（D1-D6）
- 定位：本文件是调度器设计文档的输入，需求编号将作为后续设计的追溯依据

---

## 1. 背景与现状

### 1.1 产品目标

调度器把实例 A 调度到集群中的一个节点 N，调度完成后保证：**实例 A 与节点 N 不会因为资源不足而无法正常运行**。

### 1.2 现状对照（现有代码）

| 需求 | 现状 |
|---|---|
| 按资源调度 | `SimpleScheduler`（`scheduler_impl.go`）仅轮询 + 存活过滤，不看资源 |
| 节点当前/过去占用 | `Node` 表仅静态配置（core_num/memory_size/storage_size），无动态占用、无带宽 |
| 区域偏好 | `Node.location` 存在但未参与调度；实例无 region 字段 |
| 端口调度 | `assignPorts` 在调度阶段执行，但端口不作为候选节点的硬约束 |
| game-cache | 有 `NodeGameCacheRecord`，调度器不感知 |
| enabled / 健康 | 已有：`NodeAgentStatus`、`NodeAgentHealthMonitor` 心跳探测 + `SetAlive` 过滤 |
| 排队 / 取消 | 无。调度失败直接置 `Failed`，无排队、无重试、无取消 |

结论：9 条原始需求中仅"enabled + 健康"为现状已有，其余均需新建；排队机制为全新模块。

## 2. 原始需求（R1-R9）

| 编号 | 需求描述 |
|---|---|
| R1 | 调度阶段将实例 A 调度到集群中的一个节点 |
| R2 | 根据节点当前和过去资源占用（CPU、内存、网络带宽）以及实例 A 所需资源进行调度 |
| R3 | 节点携带区域字段；根据实例 A 所需区域 R，调度器倾向（不强制）属于 R 的节点 |
| R4 | 根据节点可用端口与 A 所需端口进行调度 |
| R5 | 根据实例 A 的 game-cache 与节点可用的 game-cache 进行调度 |
| R6 | 根据 node_agent 是否 enable 进行调度 |
| R7 | 根据 node_agent 健康状态进行调度 |
| R8 | 仅资源不足而无可调度节点时排队，用户可取消；其他原因则调度失败并给出原因 |
| R9 | 调度到节点 N 后，保证实例与节点不因资源不足而无法正常运行 |

## 3. 决策记录（D1-D6）

| 编号 | 决策点 | 结论 |
|---|---|---|
| D1 | 磁盘维度 | **纳入硬约束**。容量计算包含磁盘；game-cache 下载、`/data` 恢复、快照落盘均占用磁盘 |
| D2 | 无 game-cache 的节点 | **先不调度，直接失败**。game-cache 为硬约束：节点无 `AVAILABLE` 缓存即排除；无任何候选节点有缓存时实例直接失败（结构性原因，不入队） |
| D3 | 区域节点缺失 | 默认**降级跨区域调度 + 惩罚分**；提供"区域强制"配置开关，强制模式下无区域 R 节点 → 失败 |
| D4 | 排队队列 | **持久化（落 DB）+ 支持优先级**，进程重启不丢 |
| D5 | 取消语义 | **移除出队，实例保持 stopped**，不删除实例 |
| D6 | 带宽 | **软约束评分 + request 模型**，不参与硬约束排除（实时波动大，不宜硬性卡） |
| D7 | priority 来源（OQ1） | 实例自带 `priority` 字段，默认 100；同优先级内 FIFO |
| D8 | 带宽 request 来源（OQ2） | 扩展 `game_container_config`（如 `bandwidth_request_mbps`，进/出双向） |
| D9 | 排队超时/退避默认值（OQ4） | 排队超时 30 分钟（可配置）；重试退避 15s 起、指数 2 倍、上限 5 分钟；唤醒事件触发重试时重置退避 |
| D10 | 取消与唤醒竞态（OQ5） | **降级为设计注记**：需求层仅要求"取消在任何时刻（含调度尝试进行中）都安全且不残留预留资源"（S17）；具体并发机制（状态守卫 / cancel 标记 / 乐观锁）属设计阶段决定，不属需求约束 |

## 4. 调度模型：硬约束 / 软偏好 / 评分

调度决策必须显式区分三层，避免实现时纠缠。

### 4.1 硬约束（filter，不满足直接排除该节点，记录排除原因）

| 编号 | 约束 | 说明 |
|---|---|---|
| H1 | node_agent 为 Enabled | R6 |
| H2 | node_agent 健康 | R7；非 `unknown` / `unhealthy`（首次探测前默认不可调度） |
| H3 | 资源充足 | CPU、内存、磁盘（D1）：`预留后可用 ≥ 实例 request` |
| H4 | 端口满足 | 协议 + 端口段（含连续段）可分配（R4） |
| H5 | game-cache 命中 | 节点有该 game_build 的 `AVAILABLE` 缓存（R5 + D2）；`DOWNLOADING` 不算命中 |

### 4.2 软偏好（不满足不排除，只降分）

| 编号 | 偏好 | 说明 |
|---|---|---|
| P1 | 区域 = R | R3 + D3；匹配加分，不匹配降级跨区 + 惩罚分 |
| P2 | 带宽余量大 | R2 + D6；按 request 模型评估余量，双向（进/出）P95 |
| P3 | 数据本地性 | 实例上次运行的节点加分（若本地数据仍在） |
| P4 | 负载均衡 | 节点分配利用率低者加分，避免热点 |

### 4.3 评分（score，对通过硬约束的候选排序）

```text
score = w1 * region_score        (P1)
      + w2 * bandwidth_score     (P2)
      + w3 * data_locality_score (P3)
      + w4 * load_balance_score  (P4)
```

要求：

- 权重 `w1..w4` 可配置（H1 配置化）。
- 纯函数、确定性：相同输入产生相同输出，可单测、可复现。
- 每项得分可解释：能回答"为什么选 N 不选 M"（F2 审计日志）。

## 5. 决策出口：排队 vs 失败（R8 精确化）

无可用节点时，按排除原因分类处置：

### 5.1 可恢复原因 → 排队

| 排除原因 | 性质说明 |
|---|---|
| 资源不足（CPU/内存/磁盘） | 实例释放 / 节点扩容后可能恢复 |
| 端口不足 / 端口段不可连续分配 | 实例停止后端口释放即恢复 |
| 节点全部下线 / 全部不健康 / 全部 Disabled | 运维可恢复（带排队超时，S16） |

### 5.2 不可恢复原因 → 失败（结构化原因，见 S27）

| 排除原因 | 性质说明 |
|---|---|
| 无任何注册 node_agent | 结构性 |
| 无任何节点有该 game_build 的 game-cache（D2） | 结构性（依赖 GameCacheManager 预分发，见 S10；现阶段不新增调度侧自动下载） |
| 区域强制模式（D3）下无区域 R 节点 | 结构性 |
| 配置错误（端口段超范围、资源需求超单节点容量上限等） | 结构性 |
| 游戏不被任何节点支持 | 结构性 |

### 5.3 排队/失败判定时机

排队或失败均基于**唤醒时重算的最新资源视图**（S18），而非入队/失败判定瞬间的快照。

## 6. 补充需求（S1-S36）

### A. 资源模型与度量口径（P0）

- **S1 request/limit 分离**：调度按 request 预留；limit 只作用于容器运行时限制，不参与容量计算。
- **S2 磁盘维度（D1）**：容量计算与硬约束（H3）必须包含磁盘；磁盘消耗 = 实例 `/data` + game-cache + 快照临时空间。
- **S3 "当前和过去"时间口径**：定义时间窗口（如 5 / 15 / 60 分钟）与统计口径（均值 / P95 / 峰值）并分开用途——容量判定用"预留视图 + 安全余量"，压力评分与告警用实时峰值。
- **S4 可用资源公式（防双重扣减）**：`可用 = 容量 − 已预留(已调度实例 request 之和) − 安全余量(headroom)`。实时占用只用于评分/告警，不直接参与容量判定。
- **S5 数据来源与陈旧性**：容量与占用由 node_agent 周期上报落库；超过陈旧窗口（如 3 个上报周期）视为陈旧——陈旧节点按保守值参与判定，或直接不参与硬约束判定。
- **S6 带宽模型（D6）**：进/出双向分别统计（P95）；区分"运行带宽"与"game-cache 下载突发带宽"；实例带宽需求走 request 模型（来源：扩展 `game_container_config`，见 D8），带宽仅参与评分（P2）。

### B. 决策流程（P0）

- **S7 两阶段决策**：filter（硬约束 H1-H5）→ score（4.3）→ 选最优 → **事务性预留** → 绑定节点。预留失败（被并发抢走）则重新 filter/score，不直接失败。
- **S8 预留机制（防超卖）**：选中节点后立即在 DB 扣减预留（行锁 / 乐观锁），防止并发调度同时选中同一节点导致超卖——这是保证"调度后不因资源不足失败"（R9）的核心手段。
- **S9 预留超时自动释放**：调度后续阶段失败或超时（build 准备失败、节点失联等），预留必须回滚，防止资源泄漏。
- **S10 game-cache 语义（D2 + OQ3）**：命中 = 记录状态 `AVAILABLE`；`DOWNLOADING` 不算命中；无缓存节点直接排除（H5）；无任何候选节点有缓存 → 实例直接失败（结构性原因，不入队）。**与现有自动下载逻辑的关系**：controller 侧 `GameCacheManager`（`game_cache_manager.go`）已有后台循环——周期同步分支，并对每个 Enable 分支把最新 build 下载/更新到所有已启用节点（node_agent `CacheGame`，幂等防并发双下载）。调度侧**现阶段不新增**按需下载逻辑，直接依赖该预分发机制；若实例的 game_build 未被预分发到任何节点，调度直接失败，需人工走缓存管理流程。
- **S11 区域 fallback（D3）**：默认降级跨区域调度 + 惩罚分；"区域强制"开关开启时，无区域 R 节点 → 失败（结构性原因）。

### C. 排队与取消（P0，全新机制）

- **S12 队列持久化（D4）**：排队记录落 DB，进程重启后不丢；现有 `ReconcileDispatcher.queue`（内存 channel）是工作通道，语义与排队队列不同，需要区分。
- **S13 排队状态**：`game_instance` 新增排队状态（如 `queued`），与现有 `pending` / `scheduling` 语义区分。
- **S14 唤醒触发源与防风暴**：唤醒时机包括——节点资源上报更新、节点健康恢复 / enable、端口释放、其他实例停止/删除释放资源、定时退避重试（指数退避）。一次资源释放可能唤醒一批排队实例，需节流 / 批量调度防唤醒风暴。
- **S15 优先级（D4 + D7）**：队列按 priority 排序（实例自带字段，默认 100）；同优先级内 FIFO；防止长队饥饿。
- **S16 排队超时**：最长等待时间可配置（默认值见 D9），超时自动失败并返回"排队超时"原因，不无限挂起。
- **S17 取消（D5）**：取消语义 = 移除出队，实例保持 `stopped`（不删除实例）；取消接口幂等。**需求语义**：取消在任何时刻执行都必须安全——包括排队中、以及调度尝试进行中；进行中取消不得残留已预留的资源/端口（不得因取消导致资源泄漏或状态不一致）。并发处理的具体机制（状态守卫、cancel 标记、乐观锁）属**设计阶段**事项（D10 注记），不由需求约束实现方式。
- **S18 重算视图**：排队 / 失败判定基于唤醒时最新资源视图，避免排队期间资源变化造成误判。

### D. 端口调度细化（P1）

- **S19 端口硬约束（H4）**：协议（udp/tcp）+ 连续段（现有 `GameContainerPortExcerpt`）均需满足；分配后立即标记占用（`node_ports`），防并发冲突。
- **S20 端口不足归入可恢复原因**：实例停止即释放端口，端口不足 → 排队（5.1）。
- **S21 端口释放时机**：实例停止 / 删除 / 调度失败回滚时统一释放；释放留审计。
- **S22 NAT vs HOST 模式**：现有 `PortMode` 影响端口占用计算与对外通告，调度按模式分别处理。

### E. node_agent 健康细化（P1）

- **S23 健康状态机**：`unknown(未探测) / healthy / degraded / unhealthy`，替代现有 `alive bool`；**首次探测前默认不可调度**（修正现有默认 `alive=true` 的潜在风险）。
- **S24 健康维度扩展**：连通性之外增加 agent 自身状态（磁盘满、任务队列积压、负载过高），由心跳 / 状态上报携带。
- **S25 健康恢复事件唤醒排队**：与 S14 联动。
- **S26 运行中失联边界**：实例已运行后节点失联，走开发文档的 `Uncertain` / 锁 / fencing 恢复流程，与调度器解耦；调度器只负责"新调度"与"恢复调度"的选点。

### F. 失败原因与可观测性（P1）

- **S27 结构化失败原因**：调度结果包含 code + message + **每个被排除节点的排除原因明细**（资源不足还需给出缺口量）。现有 `Schedule()` 仅返回 error string，且失败直接置 `Failed` 无明细，需改造。
- **S28 调度审计日志**：每次决策全记录——输入需求、候选节点列表、各项得分、排除原因、选中节点、耗时。
- **S29 metrics**：`schedule_attempts_total{result=success|queued|failed}`、`queue_depth`、`queue_wait_seconds`、`schedule_duration_seconds`。
- **S30 事件**：`InstanceScheduled / InstanceQueued / InstanceScheduleFailed / InstanceCancelled` 等事件接入现有事件体系。

### G. 目标验证与闭环（对应 R9，P1）

- **S31 目标转 SLO**：调度后因资源不足导致的启动失败率 = 0；节点分配利用率设上限（如 80%），接近上限不再调度（即安全余量的来源）。
- **S32 闭环反馈**：实例实际发生 OOM / 被杀 / 启动失败 → 反馈调度器（节点扣分或标记 degraded），用真实运行结果校正调度决策，而非只信上报数据。

### H. 配置化（P2）

- **S33 策略参数可配置**：评分权重、安全余量、时间窗口、队列超时 / 退避参数均可配置（yaml / env）。
- **S34 硬约束开关**：区域强制（D3）、game-cache 强制（D2 默认强制，开关用于后续放宽）。

### I. 接口与幂等（P2）

- **S35 调度幂等**：同一实例重复触发调度不重复排队、不重复预留。
- **S36 鉴权与配额**：创建 / 取消实例接口鉴权；排队数量上限防滥用。

### J. 调度边界与触发语义（P1）

- **S37 调度触发时机**：调度器处理的触发源清单——① 新实例创建（pending）；② 失败实例手动重试（failed→pending）；③ 程序重启后恢复中间态实例（现有 Recover 流程）；④ 排队实例被唤醒（S14）。调度器是"状态驱动的单入口"，不自行发明触发源。
- **S38 取消/删除的状态适用范围**：排队中（queued）可取消（D5）；调度进行中（scheduling 及后续阶段）的取消必须安全（S17）；**删除实例隐含取消排队**——删除时若实例在排队中须同时出队并释放相关资源。
- **S39 游戏支持维度澄清**：节点对游戏的"支持"由 game-cache（`AVAILABLE`）+ 运行镜像（`PrepareGameBuild` 拉取）共同体现。需明确**节点是否限定游戏集合**：若为通用节点，硬约束中无需新增"游戏类型"项（默认按此处理）；若存在游戏专用节点，需增加"节点支持该游戏"硬约束。**待确认**。
- **S40 region 来源与缺省语义**：region 是实例属性，创建实例时指定；缺省（未指定）时视为"任意区域"——区域偏好不生效，既不做区域限制也不加分。
- **S41 职责边界（防范围蔓延）**：节点资源紧张时的**实例回收/驱逐**（空闲实例停止、低优先实例驱逐）属于 controller / reconcile 职责（见开发文档 13.4 节点压力处理），**不属于调度器**；调度器只负责"新调度选点 + 排队"，两者通过状态与事件联动（如回收释放资源 → 触发排队唤醒）。

### K. 非功能性需求（NFR，P1）

- **N1 调度决策延迟**：单次调度决策（filter + score，不含排队等待）目标 < 1s，可随节点规模配置。
- **N2 高可用**：调度器作为 controller 内嵌模块，需明确单副本是否可接受；排队持久化（D4 / S12）保证进程重启不丢排队。
- **N3 规模扩展性**：目标支持节点规模需明确量级（建议 ≥ 200 节点、≥ 5000 排队实例）；评分算法支持分层过滤（先粗筛后精排）或增量索引，避免全量扫描退化。
- **N4 一致性**：资源预留与节点绑定必须原子（同一事务），任何时刻不允许两个实例对同一资源（端口 / 容量）超卖；调度决策允许基于稍陈旧的上报数据（有界陈旧，见 S5），但**预留必须严格串行化**（S8）。
- **N5 可恢复性**：调度器 / DB 故障恢复后，队列与中间态实例可恢复继续调度（现状已有 Recover 流程，纳入需求验证范围）。

## 7. 数据模型与接口影响（设计输入）

- `game_instance`：新增 `region`、资源需求（cpu/mem/disk/带宽 request）、`priority`、排队状态与排队字段（排队原因、入队时间、唤醒时间、重试次数）。
- `nodes`：新增动态资源字段（当前与历史占用：CPU/内存/磁盘/带宽）；`location` 作为区域字段参与调度。
- `node_ports`：明确预留（reserved）语义与占用事务。
- `node_agents`：健康状态字段扩展（S23）。
- `Scheduler` 接口：`Schedule()` 返回结构化结果（候选节点、评分、排除明细），不再只返回 error string。
- 新增：排队表（或复用 `game_instance` 排队字段）。

| 编号 | 问题 | 结论 | 状态 |
